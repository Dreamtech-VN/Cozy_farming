# 1. Research findings and evidence
This specification does not claim access to the original source code or server. Publicly available evidence is used to reconstruct the observable product direction, while new mechanics are explicitly specified as project features.
# 1.1 What is confirmed about the Java
A SoftGames Java title named is archived on Phoneky. One archived build is 921 KB, with 31 other versions listed for different devices/resolutions.
The public description says the player builds a zoo and improves structures including cages, souvenir shops and entertainment places.
The same description states that upgrades are gated by a small logic/arcade game in which animals are aligned into lines; higher upgrades require more lines.
The Vietnamese 2012 article identifies a mobile game distributed through MyZone and states that it was a Java game requiring GPRS for online play. However, that article's body appears to mix descriptions of an ocean/fish game, so its feature list is treated as low-confidence evidence rather than exact documentation.
The supplied screenshot is therefore the strongest visual reference for the specific Vietnamese version being targeted.

# 2.2 Core gameplay loop
LOGIN -> Load player profile + farm + zoo snapshot -> Spawn player in selected home/zoo location -> Collect ready crops / animal products -> Feed/care for animals -> Build or upgrade zoo/farm structures -> Play a mini-game for active rewards -> Sell / process resources -> Visit friends / social actions -> Complete missions -> Save server state -> Return later for offline-time progression
# 2.3 Design boundary
The project should preserve the low-resolution, readable, cozy, social feeling of the reference while upgrading the backend and client architecture. It should not become a heavy 3D tycoon. The world remains 2D, sprite-driven and highly interactive.

# 3.3 Server authority
Client never decides final currency, inventory, crop completion, animal product quantity, item ownership or purchase success.
Client sends intent: plant(seedId, plotId), harvest(plotId), buy(itemId), feed(animalId), move(x,y).
Server validates ownership, cooldown, requirements, economy price, time and state transition.
Server returns authoritative result plus revision/version.
Client may predict movement locally, but all economy and persistent state is authoritative.

# 7.1 Habitat architecture

Each animal references one habitatId and one ownerId.
Habitat upgrades change max capacity, visual level and visitor attraction.
Animal species should be data-driven using ScriptableObjects on client + canonical records in server DB.

# 7.4 Visitor simulation
Visitors are lightweight simulation agents, not persistent accounts.
Spawn/despawn zoo rating, open hours and player activity.
Visitor satisfaction = animal appeal + cleanliness + facilities + decoration + congestion penalty.
Revenue should be calculated server-side in periodic ticks rather than per visitor transaction.
Use aggregated visitor simulation to keep mobile performance stable.
# 8. Mini-game system
# 8.1 Original-inspired Animal Match-3
Board: 6×6 or 7×7 for mobile.
Tiles represent animal icons.
Match 3+ horizontally/vertically.
Combo multiplier increases score.
Objective can be 'make N lines' to unlock an upgrade, reflecting the public description.
Server validates the final reward; the board simulation can run client-side but reward calculation must be bounded by a signed/session result.
MATCH-3 SESSION createSession(seed, ruleSet) -> client plays -> client submits score + session proof -> server validates score range / move count / duration -> reward table -> transaction
# 8.2 Other mini-games
Fishing: timing/tension mini-game; catches become inventory items.
Bug catching: tap/aim window; rare bugs are collection items.
Memory cards: short daily activity.
Cooking: ingredient matching / timing.
Pet race: asynchronous race records rather than real-time physics in MVP.

# 11. Missions, daily tasks and events

# 17. Security / anti-cheat
Never trust client time, currency, item quantity, crop ready state or reward amount.
Server uses DB time/UTC for persistent timers.
Use idempotency keys on purchases, harvests, claims and rewards.
Rate-limit login, friend requests, chat, mini-game submissions and farm actions.
Detect impossible action frequency, movement speed, reward rate and inventory deltas.
Mini-game sessions need server-issued session IDs, seed/rules and bounded score validation.
Use signed configuration/content manifests for versioned client data.
Maintain an audit trail for GM/admin actions.

# 25. Final developer direction
The correct project direction is not a generic zoo tycoon. The reference product's strongest identity is a small-scale 2D social world where the player/avatar is physically present in the map, animals are visible entities, the zoo can be upgraded, and an active mini-game supports progression. The Farm layer should then extend the same loop: the player physically visits the farm, grows crops/raises livestock, produces goods, trades with friends and feeds the zoo economy. -style social systems provide the retention layer: identity, home, friends, visits, chat, fishing, collections, missions and cosmetics.

# 27.3 Vàng — Soft Currency
Vàng is the main in-game currency used during normal gameplay.
Players earn Vàng through farming, selling produce, zoo visitor revenue, missions, mini-games, quests, achievements and selected social activities.
Vàng is spent on seeds, basic animals, habitat construction, buildings, decorations, processing, shop goods, upgrades and selected NPC services.

# 27.17 Idempotency
Every purchase, claim, gacha pull, reward and currency-changing request must carry clientRequestId/idempotencyKey.
The server stores the key with the resulting response.
If the client retries because of network loss, the server returns the original result rather than executing a second transaction.
External payment transaction IDs must be unique.

# 27.19 Anti-exploit scenarios
Double tap purchase → idempotency prevents duplicate purchase.
Disconnect after gacha result → result remains stored and can be recovered.
Manipulated client clock → server timestamp is authoritative.
Modified client reward → server ignores client-provided reward amounts.
Replay old request → expired request/session or duplicate key rejected.
Concurrent purchase → wallet row lock/optimistic version prevents overspending.
Inventory overflow → validate maximum stack/capacity before grant.
Gacha manipulation → server RNG and banner rules are authoritative.
# 27.20 Monetization design boundary
Core farm/zoo progression must remain playable without spending.
The primary premium value proposition is cosmetics, customization, collection and optional convenience.
Avoid selling overwhelming direct combat/stat advantages because the product is intended as a social/cozy game.
If any gameplay acceleration is sold, cap it and clearly identify it as convenience.
Gacha should focus on cosmetic/collection outcomes where possible.
Duplicate conversion should be deterministic and documented.
Limited banners must show start/end dates and relevant rules.

Core design decision: the Farm is not a separate money-making feature. The Farm is the primary food-production and logistics system that supplies the Zoo. The Zoo is the player's visitor-facing business. Visitors enter the Zoo, consume services, and generate Vàng. Vàng is reinvested into Farm and Zoo expansion.

Farm's primary purpose is producing food and raw materials for Zoo animals.
Farm also provides processing, storage and delivery progression.
Surplus food can be sold for Vàng, but supplying the Zoo should remain the strongest strategic use.
Farm capacity must scale with Zoo animal population.

# 29.22 Zoo population management
Each habitat has a maximum capacity.
Animal count increases food demand.
Overcrowding reduces happiness and visitor satisfaction.
Animal population is therefore a strategic choice rather than an unlimited collection dump.
# 29.23 Emergency food market
Players can purchase emergency food when Farm production is insufficient.
Emergency food is deliberately more expensive than producing it on the Farm.
This prevents a hard dead-end while preserving the Farm's strategic importance.

# 29.30 Server-authoritative food tick
For each active/open Zoo: 1. Calculate habitat demand. 2. Consume feeder inventory. 3. If enabled, replenish from Zoo Warehouse. 4. If Warehouse is insufficient, mark shortage. 5. Update animal hunger/health/happiness. 6. Recalculate visitor attraction modifier. 7. Aggregate food/revenue metrics.Do not rely on the client for authoritative food consumption.Use lazy elapsed-time calculation for offline periods.
# 29.31 Offline behavior
Crops continue growing while offline.
Processing jobs continue while offline.
Animal food consumption is calculated from elapsed server time using an aggregate model.
Full visitor AI should run only while the Zoo is active; offline operation uses an aggregate rule if enabled.
On login, server returns a summarized offline result and updated inventories/stats.
# 29.32 Anti-exploit
Client cannot set crop ready time, food quantity, visitor count or revenue.
Food transfers use idempotency keys.
Currency revenue/costs create economy ledger entries.
Duplicate harvest/delivery/reward requests return the original transaction result.
Server time is authoritative for all production and visitor calculations.

# 29.35 Final design rule
The Farm answers: 'How does my Zoo get enough food?' The Zoo answers: 'How do I turn my animals and facilities into a destination visitors want to pay for?' The economy answers: 'How do I reinvest Zoo profit into a larger Farm and Zoo?' This Farm → Food → Animal → Visitor → Vàng loop is the central business simulation of the project.

# 30.27 Final architecture principle
The game should feel one connected world. Farm is the Zoo's supply chain; Zoo is the main visitor-facing business; is the player's identity; Social connects players; Exploration and mini-games provide active gameplay; Vàng drives normal progression; Kim Cương monetizes cosmetics, gacha and premium content. New systems should plug into these existing loops instead of becoming isolated features.
# 31. PROJECT TERMINOLOGY & DOCUMENTATION POLICY
All future technical, UI/UX, economy, gameplay and backend documentation must describe this project as a standalone product. Requirements, mechanics, terminology and implementation decisions must be defined directly in this specification without referencing, comparing to, or naming unrelated games, apps, platforms or third-party products.
The design vocabulary should use project-native terms such as Farm, Zoo, Habitat, Visitor, Animal, Food, Vàng, Kim Cương, Farm Level, Zoo Level, Collection, Event, Club, Exploration and Social.
